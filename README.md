# Мобильная разработка — практические задания

## О курсе

Вы работаете командами по 2–4 человека. Каждая команда разрабатывает мобильное приложение — [интернет магазин](https://www.figma.com/design/nLJepvA3O1yRnh39iK2RIT/FEFU-Store-Project?node-id=0-1&p=f) (макет будет дорабатываться – небольшие изменения в существующих экранах + новые экраны).

Задания идут блоками, каждый блок привязан к лекции. Всего 6 блоков + финальная защита. Блоки не привязаны к конкретным неделям — работаете в своём темпе, но к защите всё должно быть готово.

Те, кто сдаёт **зачёт** — делают проект с нуля. Те, кто сдаёт **экзамен** — могут начать с нуля или взять существующий проект с прошлого семестра и доводить его. Требования к каждому блоку отличаются — смотрите чек-листы.

Платформа на выбор: Android (Kotlin), iOS (Swift), Flutter, React Native. Выбираете один раз на старте, дальше работаете на нём весь курс.

Каждая команда делает ревью PR другой команды — это peer review. Вы проверяете чужой код по чек-листу, на соответствие макету, оставляете замечания и даёте (или не даёте) approve. Без approve от другой команды PR не уходит на проверку преподавателю.

## Как устроена работа

У каждой команды — свой репозиторий в организации курса. В `main` напрямую пушить нельзя — только через pull request. Каждый PR автоматически проверяет бот-ревьюер.

## Как сдавать задание

1. Создать ветку от `main` (например `hw2-catalog`)
2. Положить нужный `checklist.md` в корень репозитория (см. [Какой чек-лист выбрать](#какой-чек-лист-выбрать))
3. Сделать задание в этой ветке
4. Открыть Pull Request в `main`
5. Скинуть ссылку на PR [боту](https://t.me/feip_fefu_reviewer_bot)
6. Дождаться проверки бота (обычно 5–10 минут после последнего коммита)
7. Исправить замечания — пушить фиксы в ту же ветку, после чего снова скинуть ссылку боту
8. Получить approve от другой команды (peer review)
9. Отдать на проверку преподавателю
10. Преподаватель проверяет и мержит PR

## Бот-ревьюер

Бот: [@feip_fefu_reviewer_bot](https://t.me/feip_fefu_reviewer_bot)

Бот автоматически проверяет ваш PR по чек-листу текущего задания. Он собирает проект, смотрит код и оставляет комментарий в PR.

Бот — не финальная оценка, а помощник. Он подсказывает что исправить до того, как преподаватель посмотрит.

Что означают отметки:
- ✅ — требование выполнено
- ⚠️ — выполнено частично, есть замечания
- ❌ — не выполнено или отсутствует

## Какой чек-лист выбрать

**Блок 1** — зависит от стартовой точки:
- [hw1/new.md](hw1/new.md) — если начинаете проект с нуля
- [hw1/existing.md](hw1/existing.md) — если берёте существующий проект

**Блоки 2–6** — зависит от формы аттестации:
- `credit.md` — если у вас зачёт
- `exam.md` — если у вас экзамен

Ссылки: [hw2](hw2/) · [hw3](hw3/) · [hw4](hw4/) · [hw5](hw5/) · [hw6](hw6/)

Скопируйте нужный чек-лист в корень своего репозитория под именем `checklist.md` — бот читает именно этот файл. При переходе к следующему блоку замените содержимое `checklist.md` на новый чек-лист.

## Если что-то пошло не так

**Бот не ответил** — подождите 10 минут. Если комментарий не появился — попробуйте отправить боту ссылку еще раз. Если не помогло — напишите преподавателю.

**Бот ответил неправильно** — бот иногда ошибается. Если считаете что требование выполнено, а бот поставил ❌ — напишите об этом в комментарии к PR, преподаватель разберётся.

**Хочу перезапустить проверку** — пушните любой коммит в ветку PR (можно пустой: `git commit --allow-empty -m "retrigger review" && git push`).
